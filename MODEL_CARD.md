# Model Card — AI Risk Prediction Models

This document follows the spirit of the standard "Model Card" format
(Mitchell et al., 2019) — a short, honest reference for anyone (a
supervisor, a defense panel, a future maintainer) who needs to know what
these models are, how they were built, and where their limits are,
without reading source code.

There are **three separate models**, one per disease. They share a
training/evaluation pipeline (see "Common architecture" below) but were
evaluated and selected independently, and their data provenance differs
in a way that matters.

---

## Intended use

Risk scores are **AI-generated risk assessments for the patient's own
awareness**, surfaced alongside a plain-language "reasons" explanation and
a feature-importance breakdown. They are explicitly **not**:
- a diagnosis
- a substitute for professional medical evaluation
- validated for autonomous/unsupervised alerting
- cleared by any regulatory body (FDA, CE, etc.)

This is a student/portfolio project demonstrating a complete, honest
MLOps pipeline (data → training → evaluation → inference → API →
UI, with provenance tracked end-to-end) — not a production clinical
product.

## Common architecture

| | |
|---|---|
| Candidate algorithms | Logistic Regression, Random Forest, Gradient Boosting (scikit-learn) |
| Model selection | 5-fold stratified cross-validation on the training split, scored by ROC-AUC; best mean-CV performer is refit on the full training set — see `train.py:_compare_and_select_model()` |
| Preprocessing | `StandardScaler` in a single `Pipeline` |
| Class imbalance handling | `class_weight="balanced"` (Logistic Regression, Random Forest) or equivalent `sample_weight` (Gradient Boosting) |
| Split | Stratified 80/20 train/test |
| Pipeline version | `v2.0.0-mixed-provenance` |

**Why compare algorithms instead of hardcoding one**: no single algorithm
is uniformly best across three datasets with very different shapes (a
tiny, fairly balanced real dataset for diabetes vs. two large, heavily
imbalanced synthetic datasets for stroke/hypertension). Comparing
candidates per disease and picking by cross-validated ROC-AUC — rather
than asserting "Random Forest is the model" — is both more honest about
why each model was chosen and, in practice, changed which algorithm won
for each disease (see below).

**Feature importance normalization**: tree-based models
(`feature_importances_`) and Logistic Regression (absolute standardized
coefficients) don't naturally live on the same scale — coefficients
don't sum to 1 the way tree importances do. Whichever algorithm is
selected, `train.py` normalizes its importances to proportions of their
own sum before saving, so the "top contributing factors" UI shows
consistent, meaningful percentages regardless of which algorithm won the
comparison for a given disease.

## Stroke model

- **Data source**: SYNTHETIC, n=30,000 (raised from an earlier n=8,000 —
  see "Dataset sizing" below for why). Generated by `data_synthesis.py`
  using a weighted-logit + sigmoid sampling process, calibrated so that
  prevalence and comorbidity rates (~4.9% stroke, ~9.2% hypertension
  history, ~4.95% heart disease history) match the aggregate statistics
  of the real, widely-used Kaggle "Stroke Prediction Dataset" — but no
  real patient rows are used. See `feature_schema.py` for why: the real
  dataset encodes hypertension/heart disease as yes/no flags, not the
  continuous vitals (systolic BP, heart rate) this app actually collects.
- **Features**: age, gender, hypertension history (flag), heart disease
  history (flag), average glucose level, BMI, systolic BP, heart rate.
  Systolic BP specifically (not diastolic) — the Framingham Stroke Risk
  Profile (Wolf et al., 1991), the standard clinical stroke-risk
  equation, uses systolic BP as its blood-pressure input. Isolated
  systolic hypertension (arterial stiffening raises systolic while
  diastolic plateaus or falls) becomes the dominant BP pattern with age,
  and it's systolic elevation specifically that correlates most strongly
  with stroke risk. Contrast with the hypertension model below, which
  needs both systolic and diastolic — a BP reading is diagnosed from the
  pair together, so dropping either number there would be arbitrary in a
  way it isn't here.
- **Algorithm selected**: Logistic Regression (CV ROC-AUC 0.798, vs.
  0.783 for Random Forest and 0.790 for Gradient Boosting — a close
  comparison, won on cross-validated ranking ability).
- **Metrics** (held-out test set, n=6,000; ~1,323 positive examples in
  the full 30,000-row dataset, up from ~340 at the old n=8,000):

  | Accuracy | Precision | Recall | ROC-AUC | Brier score |
  |---|---|---|---|---|
  | 69.3% | 9.7% | 71.7% | 0.764 | 0.192 |

- **Top feature by importance**: age (37.7%), followed by average
  glucose (15.5%) and systolic BP (13.5%).
- **Known limitation**: precision at the 0.5 cutoff is still low. At the
  realistic ~4.4% positive rate this data was calibrated to, most "high
  risk" flags will be false positives even with 4x more training data
  than before — this is a direct, expected consequence of the class
  balancing weighting recall over precision at rare-event prevalence, not
  a data-volume problem alone. ROC-AUC of 0.764 (up from 0.755) says the
  model separates risk somewhat better in *ranking* terms with the larger
  dataset; the binary threshold is what structurally struggles at this
  prevalence. See the threshold table below for the recall/precision
  tradeoff at different alert cutoffs.

## Diabetes model

- **Data source**: **REAL + bootstrap-augmented.** The Pima Indians
  Diabetes Dataset (Smith et al., 1988, National Institute of Diabetes
  and Digestive and Kidney Diseases; public domain, UCI Machine Learning
  Repository) — 724 real patient records after dropping rows with the
  dataset's zero-as-missing encoding for glucose/BP/BMI (all female,
  Pima Indian heritage, age 21+) — PLUS 2,172 bootstrap-augmented rows:
  each real row resampled 3x with small Gaussian jitter (8% of that
  row's own class-wise feature std), producing 2,896 total training
  rows. See "Dataset sizing" below and `real_data.py` for exactly how
  and why. **Every augmented row is a jittered copy of a real patient's
  data — augmentation does not add new independent information, it makes
  better use of the 724 real rows that exist.**
- **Features**: age, BMI, glucose, diastolic BP. (Deliberately different
  from the other two models — this is what the real dataset provides;
  it doesn't have systolic BP or heart rate.)
- **Algorithm selected**: Gradient Boosting (CV ROC-AUC 0.890, vs. 0.885
  for Random Forest and 0.828 for Logistic Regression).
- **Metrics** (held-out test set, n=580):

  | Accuracy | Precision | Recall | ROC-AUC | Brier score |
  |---|---|---|---|---|
  | 78.1% | 64.9% | 78.9% | 0.884 | 0.139 |

  (Previous version, real data only, n=145 test / n=579 train: 67.6%
  accuracy, 52.1% precision, 76.0% recall, 0.779 ROC-AUC — augmentation
  plus algorithm comparison moved every metric in the right direction.)

- **Top feature by importance**: glucose, followed by BMI and age —
  clinically sensible, and a good sanity check that the model learned
  real signal rather than an artifact of the augmentation.
- **Known limitation**: the underlying information content is still 724
  real records from a single population (Pima Indian women in Arizona,
  1980s) — augmentation improves how much the model can learn from those
  724 points, it does not manufacture new populations or new patients.
  Demographic narrowness remains this model's limitation; it does not
  generalize to a general patient population, and that claim would be
  false regardless of how much jittered augmentation sits on top of it.

## Hypertension model

- **Data source**: SYNTHETIC, epidemiologically-informed, n=30,000
  (raised from n=8,000 — same rationale as stroke above; no direct
  real-data equivalent exists that matches this app's continuous-vitals
  feature set).
- **Features**: age, BMI, gender, systolic BP, diastolic BP, heart rate,
  glucose.
- **Algorithm selected**: Logistic Regression (CV ROC-AUC 0.845, vs.
  0.834 for Random Forest and 0.835 for Gradient Boosting).
- **Metrics** (held-out test set, n=6,000; ~1,244 positive examples in
  the full 30,000-row dataset, up from ~370 at the old n=8,000):

  | Accuracy | Precision | Recall | ROC-AUC | Brier score |
  |---|---|---|---|---|
  | 76.4% | 12.5% | 77.9% | 0.852 | 0.159 |

- **Top feature by importance**: systolic BP (36.1%), followed by
  diastolic BP (25.2%) — as expected, since both are direct components
  of the outcome being predicted.
- **Known limitation**: same precision-at-low-prevalence caveat as
  stroke — ROC-AUC improved (0.825 → 0.852) with more data, recall
  improved substantially (55.4% → 77.9%), but precision at the raw 0.5
  cutoff remains a structural consequence of the ~4% base rate combined
  with balanced class weighting favoring recall.

## Dataset sizing — what changed and why

The original synthetic datasets (n=8,000 for stroke/hypertension) yielded
only ~340-370 positive examples per model at their ~4-5% real-world
prevalence — too few for any classifier to learn a stable minority-class
decision boundary. The original diabetes model used only the 724 usable
real Pima rows with no augmentation. Two changes address this directly:

1. **Stroke and hypertension**: default synthetic sample size raised from
   8,000 to 30,000 rows (`data_synthesis.py`). This is a generation-time
   parameter change only — the same epidemiologically-calibrated
   logit/sigmoid process, just more samples from it — so it doesn't
   change what the data represents, only how much of it exists. Positive
   examples per model went from ~340-370 to ~1,240-1,320.
2. **Diabetes**: the 724 real rows are supplemented with 2,172
   bootstrap-augmented rows (Gaussian-jittered near-duplicates of real
   points, per class) — see `real_data.py:load_real_diabetes_dataset_augmented()`.
   This is NOT additional real data and is labeled as such everywhere it
   surfaces (`data_source` field, this document, the training report) —
   it makes better use of the real data that exists rather than
   pretending there's more independent information than there is.

Combined with the new model-comparison step (see "Common architecture"),
every metric moved in the right direction versus the previous version —
most dramatically for diabetes (ROC-AUC 0.779 → 0.884), more modestly for
stroke/hypertension where the fundamental constraint (rare-event
precision at a fixed prevalence) doesn't fully resolve with volume alone.

## Threshold sensitivity (all three models)

The app doesn't act on a bare 0.5 cutoff — `risk_score` is bucketed into
`low` / `moderate` / `high` / `critical` (see
`inference.py:RISK_LEVEL_THRESHOLDS`, itself flagged in-code as a
starting point that should be clinician-tuned before any real deployment
rather than left as a flat default). Precision/recall look very
different depending on which cutoff you evaluate at:

| Model | Cutoff 0.25 (moderate+) | Cutoff 0.5 (high+) |
|---|---|---|
| Stroke | P 6.4% / R 90.9% | P 9.7% / R 71.7% |
| Diabetes | P 55.3% / R 96.5% | P 64.9% / R 78.9% |
| Hypertension | P 7.4% / R 94.8% | P 12.5% / R 77.9% |

**Why this table matters for the defense**: it shows the precision/recall
tradeoff is a deliberate design choice, not an accident. At the loose
0.25 cutoff, the system deliberately favors recall (catching nearly all
real cases) over precision, on the reasoning that in a monitoring
context, missing a genuine risk case is more costly than an extra
false-positive alert the patient/AI Assistant flags for professional
follow-up and gets dismissed.

## Predictive Trend Forecasting

This is a separate capability from the three risk models above — it doesn't
classify current risk, it projects a vital's likely near-future trajectory.
It's documented here because it's evaluated with the same honesty standard
as the risk models: a stated confidence figure, explicit failure modes, and
no result presented with more certainty than the underlying data supports.

**How it works** (`app/services/trend_analysis.py:forecast_trend()`):
ordinary least-squares linear regression of a vital's value against days
since the first reading in the window, fit with a closed-form calculation
(no ML library needed for this — deliberately kept as simple, auditable
arithmetic, consistent with the rest of the trend module being rule-based
rather than learned). From the fitted line and the patient's current normal
range, the system projects whether/when that line would cross a clinical
threshold — and, if the patient is already outside the range, whether the
trend is heading back toward it or further away.

**Confidence gating — this is the part that matters most.** A forecast
is only returned when:
- at least 4 readings exist for that field,
- they span at least 2 days (a handful of same-day readings can't support
  a day-scale projection),
- and the linear fit's R² is at least 0.30 (i.e. the straight line
  explains at least 30% of the variance in recent readings).

Fail any of these, and the system returns *why* — "not enough readings
yet," "these readings don't follow a clear enough trend to project," etc.
— rather than a number computed from noise. This matters in practice: a
patient whose readings are genuinely fluctuating (no real trend) will
correctly get no forecast, not a misleadingly precise one.

**Comparison to an existing commercial system.** Biofourmis (a
venture-funded RPM platform, $143M+ raised) markets AI-based prediction of
"disease trajectory" — projecting where a patient is headed before it
happens — as its core differentiator, applied to heart failure,
hypertension, diabetes, and AFib. Their methodology isn't published; it's
a black-box result surfaced to a clinical "health navigator." This
project's forecasting is deliberately built the opposite way:

| | Biofourmis (commercial) | This project |
|---|---|---|
| Methodology | Undisclosed | Ordinary least-squares regression, documented and auditable |
| Confidence shown to the end user | Not disclosed | R² shown alongside every forecast |
| Behavior when data doesn't support a projection | Unknown | Explicitly fails safe — returns a stated reason, not a guess |
| Who sees it | Routed through a human "health navigator" first | Shown directly to the patient, framed as a projection, with the AI Assistant (see its own hard-rule #6) required to relay it only as a projection, never as a certainty |

The claim here isn't "more accurate than Biofourmis" — that's not
verifiable without their data or methodology. The claim is narrower and
demonstrable from this codebase alone: the same category of feature,
built transparently, with its confidence and failure modes exposed rather
than hidden.

## What would need to change before any real-world use

1. Real, IRB-approved (or otherwise ethically-sourced and
   consented) clinical data for stroke and hypertension, matching this
   app's actual feature set — bootstrap augmentation (as used for
   diabetes) narrows the *usability* gap of a small real dataset, it does
   not substitute for real data where none exists at all.
2. External validation on a population distinct from the training
   population — including for diabetes, given the Pima dataset's
   demographic narrowness (which augmentation does not address).
3. Clinician and biostatistician review of feature choices, thresholds,
   and the four-tier risk-level cutoffs.
4. A defined regulatory pathway (e.g. explicit "clinical decision
   support, not a diagnostic device" positioning, or formal
   FDA/CE clearance if positioned as a diagnostic tool).
5. Prospective evaluation (does the model change outcomes when actually
   used by clinicians?), not just retrospective accuracy on a held-out
   split of training-time data.
